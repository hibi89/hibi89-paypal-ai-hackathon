## 2. 방식 두 가지 비교 및 권고

| 조건 | A: 세 모듈 API/화면 동시 착수 | B: 결제 실증 우선 + 병렬 모듈 |
|---|---|---|
| 추진 순서 | 3명 독립 구현 후 마지막 통합 | 공통 계약/샌드박스 확인 후 3명이 계약에 맞춰 병렬 개발 |
| 속도 | 초기 코드는 많지만 API/상태 충돌 위험 | 초기 POC 시간이 필요하나 통합 결함이 일찍 드러남 |
| 비용·한도 | 실험·AI 호출·디버깅 분산 | Sandbox 코어 집중, 후속 모듈 API 검증 가능할 때만 확대 |

## 4. 역할별 계약과 소유권

- **총괄 `lead/paypal`**: PayPal SDK/API 실현성, AI+PayPal 통합 설계, 데이터 계약, 테스트 검수, PR 통합, 영상/영문 제출, 상위 보고. 코드 구현 직접 필요 시 자기 승인된 경로에서만 최소 수정. `main`은 검증 통합 기준, 강제푸시 금지.
- **`feature/quote-payment` 담당**: AI 입력→가격 후보·근거→판매자/고객 조건 승인→서버 검증→Sandbox Orders v2 주문/승인/캡처→실제 상태 조회. 모델의 임의 가격/명령을 곧바로 실행 금지.
- **`feature/delivery` 담당**: 계약·마일스톤·납품 상태, 사용자의 승인/검수 및 결제 상태 연결. 납품을 PayPal 자금 예치/에스크로와 혼동하지 않음.
- **`feature/subscriptions` 담당**: 정기 계약 상태, PayPal Subscriptions/Webhooks 계정 가용성 검증, 실패/취소/중복 수신·재시도 상태. 실제 미지원 기능은 지원으로 표시하지 않음.
- **데이터 계약 v0(잠정):** Quote {id, price_minor, currency, approval_status}; Payment {quote_id, paypal_order_id, capture_id, status, idempotency_key}; Milestone {project_id, stage, delivery_status}; Subscription {project_id, paypal_subscription_id, billing_status}; Event {source_id, type, received_at, processed_at}. 상세 필드/DB는 승인 뒤 동결. 결제 상태·납품 상태·구독 상태는 별개이고 사용자 조회는 영속 DB를 읽으며 페이지 새로고침 시 결제 재실행 불가.

## 5. 테스트/완료 판정

1. 작동: Sandbox 실제 주문 생성→승인→캡처 및 상태 조회. 문서상 API 가능성과 실제 호출 성공 구별.
2. 안전: 서버 금액 검증, 승인 없는 자동 결제/재캡처 금지, PayPal-Request-Id 키 보존, 에러 타임아웃 뒤 상태 재조회, 비밀정보/고객 개인정보 비공개.
3. 중복/복구: 이중 클릭, 새로고침, 같은 Webhook 2회, 결제 승인 취소, API 오류, DB/네트워크 일시 장애 테스트.
4. 서비스: 빌드·서버 HTTP·브라우저 렌더·Console/Network·API 결과·UI 상태 교차 검사. CI/Ready만으로 정상 판정하지 않는다.
5. 심사: 제3자용 공개 GitHub+LICENSE, 3분 미만 공개 YouTube 영상, 영문 설명/실행 안내, 심사 기간 무료 접근 유지.
6. 증빙: 단계별 실제 실행 로그·GitHub SHA·테스트 PASS/FAIL·Sandbox 실 API 또는 모의인지·Devpost 영수증을 STATUS/HANDOFF에 분리 기록.

- **11/08 배포/브라우저 실패**: 실제 URL 대신 공개 재현 가능한 로컬 설치+실행안내 경로가 규정상 허용됨. 비밀키는 Public GitHub에 노출하지 않고 별도 합법적 심사 접근 절차 마련.

# Proofline 3×3 opportunity discovery — functional baseline (2026-10-31 KST)

## Goal and current scope
One Proofline marketplace with AI Work and Global Services on the SAME offline quote → approval → unpaid contract backend. For each owner-initiated fictional brief, show three differing candidate archetypes: Professional, Rising Talent and Newcomer. Permit exactly two more owner-clicked rounds; show 3 distinct candidates per round, nine total, and preserve prior sets with clickable history. A buyer may choose any **fully skill-eligible fictional example** in the shown or prior set. Missing required skills must be visible and cannot silently prepare a full-scope quote. The three tiers are illustrative discovery slots and are NOT measured skill, seniority, outcome, pricing, reputation or verified under-valuation. No real seller registrations, actual prices or Gemini/PayPal requests.

## Product / integration baseline
- Runtime: existing Node.js 22+ ES modules and local HTTP loopback-only server; existing `node:sqlite` (no new dependency), JS DOM app, Chrome/Playwright + Node/GitHub Actions.
- Main code owner: `hibi89/hibi89-paypal-ai-hackathon@lead/paypal`. No modules imported from external repos. No new project, account, permission, service, domain or deployment.
- Inputs: category `ai_work|general_services` + 8–500-character synthetic brief. Server derives recognized skill taxonomy; match engine assembles each fixed three-member fictional scenario round from nine candidates per category.
- Comparison: A) in-memory Map: slightly simpler; restart/refresh and concurrent client behavior weaker, no crash-safe state. B) SQLite transaction/store: small local disk cost, bounded 24 owner sessions; persistent across browser reload and direct DB reopen, atomic double-click guard; **B chosen**.
- State owner: isolated local `recommendation_history.sqlite` under the ephemeral demo directory. Stores opaque ID (128-bit random), synthetic actor ID, category, SHA-256 of normalized brief, recognized skills JSON, 0-based round [0..2], created timestamp. It does NOT store raw briefs, media, real seller records or payment details. App server deletes the entire demo temp directory on graceful close; **not persistent across restarting the demo process**. Production durable auth/storage is not implemented.
- APIs: `POST /api/demo/marketplace` {brief,vertical} (first match or idempotent resume matching category/brief); `GET /api/demo/marketplace/history?sessionId=<id>` (owner-scoped read, no quota changes); `POST /api/demo/marketplace/next` {sessionId,expectedRound} (CSRF-bound atomic increment, max two). Responses include `sessionId`, `round` (1..3), `maxRounds=3`, `remainingRefreshes` (2..0), `history` with prior 3-member sets and existing skill-eligibility flags. Stale expected round returns 409, second/third retry cannot consume two more sets; quota exhausted 409.
- UI: text-based fictional status for each role, evidence/skill gaps, current count, next-three button, history buttons; old set can be reopened without refunding spent quota. Existing quote preparation is a separate human click. Client renders text via `textContent`, never raw HTML.
- Security/cost: owner-only synthetic demo session + origin/CSRF for writes + random session ID/owner check for history + bounded JSON/brief + local HTTP global rate limiter. No provider API calls, AI billing, PayPal Orders/Capture, unauthenticated public user data, or release. Real-world identities/ranking, fraud controls, price evidence and production authentication remain unimplemented.

## Confirmed 2026-10-31 P0 same-ledger integration update

- **Selected design A (implemented offline):** Reuse existing quote/contract SQLite DB for `quote_candidate_bindings` and immutable `contract_candidate_evidence`, with `BEGIN IMMEDIATE`, quote CAS and SQLite contract insert trigger. No new database dependency/cost; prior quote/contract records preserved. The 3×3 recommendation roster remains a separate *read-only selection input*, not part of a multi-table transaction; candidate evidence copied to the single source-of-truth ledger before approval.
- **Design B (deferred, not approved):** External auth provider + independent PostgreSQL/Redis service and data migrations could support real user/merchant tenancy, but has added cost, permissions, operational risk and schema change. **Do not implement or deploy without explicit owner approval.**
- **Measured acceptance:** Exact source `2968e069a885eb9daa474192bebfa9aaee8525a3` [CI](https://github.com/hibi89/hibi89-paypal-ai-hackathon/actions/runs/41186809605) 584/584 Node, Chromium two categories, Windows PASS; [offline smoke](https://github.com/hibi89/hibi89-paypal-ai-hackathon/actions/runs/41186809611) SUCCESS. Candidate binding and contract snapshot survive reopen in a persistent SQLite unit fixture, whereas the *demo application's* temp folder is intentionally deleted at shutdown.
- **Remaining hard gates:** This is **local synthetic** backend, not real seller identity/authentication, historical owner real provider receipt re-attestation, production auth/hosting, real checkout/capture or Devpost. No public exposure or API POST without consent. Existing split-file factory still present for compatibility but is no longer used by `startOfflineDemo`.
